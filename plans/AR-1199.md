# AR-1199: Expose the authenticated `asb tui install` router

## Outcome

Provide the ASB-owned, renderer-neutral command and local control boundary needed for the
standalone `asb-tui` installer. The command must delegate installation to the verified
asb-tui lifecycle contract without embedding Ratatui, terminal rendering, or TUI application
state in ASB.

## Dependencies and ownership

Dependencies: AR-1018, AR-1019, AR-1020, AR-1160, AR-1190, and AR-1191. Repository:
`martin-beck/agent-systems-benchmark`. Own only CLI routing, authenticated local broker/control
endpoint, capability advertisement, protocol fixtures, and integration tests. The standalone
application and all rendering remain in `martin-beck/asb-tui`.

## Work sequence

1. Add an explicit `asb tui` command family with `install`, `status`, `upgrade`, `remove`, and
   `launch`/interactive handoff routes. Keep existing commands unchanged and reject ambiguous,
   unknown, unsafe, or unsupported arguments with stable structured errors.
2. Expose the authenticated local control endpoint required by the standalone client. Advertise
   catalog v1.4 and lifecycle v1.5 only when the corresponding backend capability is wired;
   never report capability availability while returning a placeholder or `CapabilityUnavailable`.
3. Forward signed bundle identity, catalog digest/generation, target, protocol, operation ID, and
   idempotency binding without rewriting them. Keep credentials out of argv, control frames,
   logs, and public errors; use owner-private paths and bounded frames.
4. Make install, retry, cancel, status, upgrade, launch, and remove restart-safe and idempotent;
   preserve ASB runs and configuration when the TUI disconnects or is removed. Fail closed on
   stale catalog/runner generations, mismatched releases, malformed responses, unavailable
   providers, and partial installation state.
5. Add clean-home and fault-injection integration tests using a synthetic signed bundle and a
   fake authenticated TUI client. Qualify both success and every negative boundary, then update
   the CLI and cross-repository documentation with exact revision pins.

## Acceptance criteria

`asb tui install` is a discoverable, authenticated, end-to-end route to the standalone lifecycle
implementation; it installs only a verified compatible bundle, reports progress and actionable
failure, and can be retried safely. `status`, `upgrade`, `remove`, and launch handoff are
read-only or transactional as appropriate and do not alter benchmark state. Tests prove exact
wire preservation, capability truthfulness, identity/generation fencing, privacy, interruption
recovery, idempotence, and clean removal. No ASB renderer, Ratatui, Crossterm, or TUI application
code is added.

## Evidence and completion

Record exact signed heads for ASB and asb-tui, independent review, DCO/SSH verification, all
hosted checks, clean-home native sessions, and post-merge exact-main workflows. Do not claim
`asb tui install` is usable from source-only or protocol-only evidence.
