# AR-0815: Manage remote benchmark run lifecycles

## Outcome

Let a remote TUI validate and launch runs, disconnect freely, then reconnect from the same or another authorized controller to manage runner-owned work.

## Dependencies and ownership

Dependencies: AR-0805, AR-0814, AR-0819.
Owned paths: remote run-plan preflight, idempotent launch, detach/reattach, status projection, cancellation, conflict handling, and integration tests.
Branch: `feature/remote-run-lifecycle`. Worktree: `agent-systems-benchmark-remote-run-lifecycle`.

## Work sequence

1. Resolve agent/provider/workload/platform capabilities on the runner and return a signed/redacted effective-plan preview to the controller before confirmation.
2. Launch with runner-issued plan digest plus client idempotency key; return durable run ID/revision before event following.
3. Treat client close, laptop sleep, SSH loss, terminal exit, process kill, or network partition as detach only; no connection lifetime owns a run.
4. Reconnect/list/adopt authorized runs by stable IDs, resume status from cursors, reconcile stale commands, and manage explicit cancellation or other supported controls.
5. Keep workload/project material, credentials, raw prompts/responses, transcripts, and private artifacts on the runner; transfer only bounded privacy-reviewed summaries unless an explicit authorized export is requested.
6. Test duplicate launch, lost launch reply, simultaneous controllers, conflicting cancellation, runner restart, controller clock drift, partition healing, retention, and authorization change mid-run.

## Acceptance criteria

The canonical two-machine scenario works end to end; an acknowledged launch survives immediate controller power loss; retries cannot duplicate it; reconnect shows authoritative status and history; multiple clients obey deterministic conflict policy; remote cancel is explicit and durably acknowledged; and default control traffic never copies project material or sensitive run content to the controller.

## Evidence and completion

Record sanitized sequence traces, run/revision transitions, network fault evidence, immutable commits, independent review, exact-head CI, long disconnect/reconnect tests, and remaining lifecycle limits.
