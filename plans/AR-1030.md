# AR-1030: Resolve the Ratatui dependency closure

## Outcome

Produce a reviewed, reproducible dependency decision that allows the maintained Ratatui release to
be used by the standalone `martin-beck/asb-tui` application without silent allow-list changes,
unbounded duplicate exemptions, mutable Git dependencies, or an unmaintained private vendor fork.

## Dependencies and ownership

Dependency: AR-1017. Repository: `martin-beck/asb-tui`. Owned paths are limited to Cargo manifests
and lockfile, `deny.toml`, SBOM/provenance, dependency-policy documentation, and executable policy
tests. This AR does not own renderer, widget, terminal event-loop, ASB product, or runner code.
Branch: `build/ratatui-dependency-closure`. Worktree:
`agent-systems-benchmark-asb-tui-ratatui-dependency-closure`.

## Recorded baseline

With Ratatui 0.30.2, defaults disabled and the 0.29 Crossterm backend, `cargo audit` is clean but
`cargo deny` rejects: foldhash 0.2.0 because Zlib is absent from the allow-list; hashbrown 0.16.1
and 0.17.1 because Kasuari and Ratatui require incompatible maintained lines; and syn 2.0.119 and
3.0.5 through the released backend closure. Downstream features cannot unify or disable these
transitive defaults.

## Work sequence

1. Reproduce the exact graph from a clean lockfile and record `cargo tree -e features`, license,
   advisory, source, duplicate, MSRV, and target-specific evidence for supported Linux targets.
2. Prefer maintained upstream changes: define the smallest Kasuari/Ratatui selectable-collection or
   default-feature boundary, obtain review, and consume only immutable crates.io releases.
3. If upstream release timing blocks delivery, conduct an explicit alternative policy review:
   establish Zlib compatibility; threat-model foldhash for bounded untrusted UI data; justify each
   exact-version duplicate; and use only version-bounded exceptions with named removal conditions.
4. Add tests that fail on any additional license, duplicate, advisory, source, feature, or exception
   and verify the exception set cannot silently widen during an update.
5. Generate an exact SBOM and source/license inventory; run native x86_64 and available pinned
   AArch64 dependency/build checks without claiming unavailable native execution.
6. Document the selected decision and rejected alternatives. Do not declare Ratatui approved until
   independent review and every applicable supply-chain gate passes on the immutable tree.

## Acceptance criteria

The exact Ratatui/Crossterm graph is immutable, advisory-clean, license-compatible, source-pinned,
MSRV-compatible, and accepted by fail-closed automated policy. Any exception is exact-version
bounded, risk-justified, tested against widening, assigned a removal condition, and visible in the
release SBOM. No ASB repository code or actual TUI application code changes under this AR.

## Evidence

Record exact crate versions/checksums/features/sources, upstream references or policy-review record,
license texts, threat model, `cargo deny`/`cargo audit`, duplicate sentinels, SBOM validation,
supported-target builds, signed+DCO commit, independent full-diff review, exact-head CI, and
post-merge verification.
