# AR-0803: Define the frontend control API

## Outcome

Create a stable, bounded API that lets an independent frontend inspect and control the persistent runner without sharing UI state with benchmark execution.

## Dependencies and ownership

Dependencies: AR-0101, AR-0104, AR-0204, AR-0801.
Owned paths: frontend protocol types/schemas, runner control endpoint, read models, client library, and fault/conformance tests.
Branch: `feature/frontend-control-api`. Worktree: `agent-systems-benchmark-frontend-control-api`.

## Work sequence

1. Define version-negotiated requests/events for capabilities, settings validation, plan creation, launch, status, cancellation, history, repeat, and analysis.
2. Use length-prefixed JSON-RPC 2.0 over an owner-only Unix-domain socket on Linux, with peer-credential checks, bounded frames, explicit deadlines, pagination, backpressure, causal run/attempt IDs, and reconnect cursors. Do not auto-bind TCP merely because the frontend is reached over SSH.
3. Keep runner journals authoritative; frontend disconnect, duplicate request, retry, or crash cannot duplicate or corrupt a run.
4. Separate public summaries from sensitive artifacts and enforce least-privilege artifact access.
5. Add malformed, stale, duplicate, oversized, slow-client, disconnect, restart, authorization, and compatibility tests plus formal state invariants.

## Acceptance criteria

The runner starts and completes without a frontend; killing/restarting the frontend does not alter a run; every mutation is idempotent or explicitly rejected; status can reconnect without loss or unbounded buffering; socket path/ownership/permissions and peer identity are verified; protocol mismatches fail closed; no implicit network listener exists; and no raw credential, prompt/response, transcript, private path, or unsafe log reaches the default API.

## Evidence and completion

Record protocol fixtures, proofs, fault injection, immutable commits, reviews, exact-head CI, resource bounds, and post-merge recovery checks.
