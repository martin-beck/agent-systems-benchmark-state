# AR-0856: Add OpenJiuwen and WorkBuddy agent support

## Outcome

Add separate, capability-accurate OpenJiuwen and WorkBuddy agent adapters that translate the common
agent contract and provider profile without silent defaults. Each adapter must prove a real,
version-pinned, credential-free loopback editing journey and deterministic strict replay before the
support matrix can advertise it.

## Work sequence

1. Locate the official upstream source and distribution for each agent. Pin an immutable source
   revision, release tag, executable/package digest, lock or dependency closure, license texts, and
   supported platform/architecture. Verify the installed executable identifies the same version and
   digest before it can start. Fail closed on missing, mutable, mismatched, or unapproved artifacts.
2. Document the exact noninteractive or API protocol from pinned source. Record framing, lifecycle,
   tool calls/results, edits, usage, terminal outcomes, errors, retries, cancellation, and process-tree
   cleanup. If an agent has no executable bounded machine interface, leave that adapter unsupported.
3. Implement isolated adapter modules with private mode-0700 state, an explicit workspace root,
   cleared ambient configuration, bounded argv/environment/events/actions/turns/output/deadlines, and
   loopback-only provider routing. Translate the AR-0310 provider profile exactly or reject it before
   process start; never substitute a model, endpoint, credential mode, tool policy, or sampling value.
4. Register each adapter and only the capabilities observed at its public consumer boundary. Live
   streaming may be advertised only when a caller can consume events incrementally. Unsupported
   provider, model, setting, tool, platform, architecture, isolation, and replay combinations must be
   explicit typed rejections.
5. Check in version-pinned, privacy-reviewed public fixtures produced by credential-free loopback
   sessions. Preserve causally ordered lifecycle, edit, tool, usage, cancellation, retry, terminal,
   and cleanup evidence with stable public sentinels and no raw prompts, credentials, authorization
   material, host-private paths, user names, or machine identifiers.
6. Prove live and replay paths independently. Live tests must exercise a real pinned executable
   against a loopback fake provider, make a real isolated file edit, observe tool and usage evidence,
   cancel an owned process tree, and deny non-loopback network. Capture/seal the sanitized record,
   then strict replay must reproduce grading-relevant events and edits with network disabled.
7. Add negatives for missing/wrong executable version or digest, incomplete license closure,
   malformed/unknown/duplicate/out-of-order/oversized events, missing or conflicting terminal events,
   zero or inconsistent usage, retry exhaustion, stalled/trickled output, cancellation races, child
   escape, symlink/root overlap, ambient config/dotenv/credential leakage, non-loopback endpoints,
   unsupported provider fields, corrupted/truncated replay records, and private-data sentinels.
8. Update adapter documentation and the support matrix only with executable evidence. List exact
   version, source/package/license pins, protocol mode, tested provider/profile, platform and
   architecture, live/replay status, and every unsupported or merely build-checked combination.
9. Run focused tests, full workspace fmt/clippy/tests/docs/release build, privacy and Gitleaks checks,
   dependency/license/SBOM validation, replay/formal/fault gates, and applicable native x86_64 and
   aarch64 checks. Publish only an independently reviewed SSH-signed+DCO exact-tree candidate.

## Acceptance criteria

- Each advertised agent resolves to one immutable official source and executable/package identity;
  the complete dependency and license closure is recorded and verified offline.
- Each adapter validates identity, roots, topology, configuration, provider translation, and support
  before any workspace/state mutation or process start.
- A pinned real executable completes a credential-free loopback editing journey with bounded
  lifecycle, tool, grading-relevant edit, positive and internally consistent usage, terminal outcome,
  cancellation, owned-process cleanup, and non-loopback network denial evidence.
- A sealed sanitized record from that journey replays strictly with network disabled and reproduces
  the expected causal event/tool/edit/usage/terminal evidence; malformed or mismatched records fail.
- Capability registration exactly matches observable public behavior. Unsupported or lossy routes
  fail explicitly, and no adapter silently falls back to ambient credentials, config, model, endpoint,
  permissions, telemetry, tools, or network.
- Fixtures, diagnostics, logs, argv, environment evidence, replay records, and documentation pass the
  repository privacy policy and contain no credential or host-private data.
- Documentation and the support matrix distinguish native-qualified, replay-qualified, build-only,
  and unsupported platform/architecture/provider combinations using exact evidence references.
- Focused, full, native, privacy, dependency/license, SBOM, fault/formal, exact-head CI, independent
  review, and post-merge checks are green on the immutable tree before release.

## Evidence limits

- Parser/unit fixtures, mocks, source inspection, compilation, or an executable version string alone
  do not qualify an agent, protocol, provider, platform, architecture, cancellation, or tool behavior.
- A live run without a sealed strict replay does not prove replay support; replay alone does not prove
  the pinned executable can run. One platform or architecture does not imply another.
- No support claim is allowed without a locally executable pinned distribution whose source,
  dependency closure, license, digest, protocol, and effective provider settings are independently
  verified. If either OpenJiuwen or WorkBuddy cannot meet that boundary, keep it explicitly planned or
  unsupported rather than substituting a mock, compatible-looking SDK, mutable package, or private
  consumer credential.
- Loopback qualification proves only the declared provider/profile and bounded public fixture. It does
  not claim external service availability, consumer-account behavior, arbitrary plugins, autonomous
  permissions, telemetry safety outside the isolated boundary, or production workload quality.
