# AR-0602: Validate CSB monitoring and contention diagnostics

## Outcome

Establish exactly which resource, system-statistics, and kernel-contention evidence a pinned
CSB revision can contribute to ASB, integrate only independently validated signals, and report
unsupported signals as unavailable rather than zero or inferred.

## Dependencies and ownership

Dependencies: AR-0201, AR-0202, AR-0601.
Owned paths: the optional asb-csb monitoring bridge, CSB-to-ASB metric mapping, controlled
contention fixtures, compatibility records, and monitoring documentation.
Branch: feature/csb-monitoring-contention. Worktree:
agent-systems-benchmark-csb-monitoring-contention. One worker owns this task; shared Cargo,
schema, and release edits require coordinator integration.

## Work sequence

1. Pin and inspect CSB source, licenses, MonitorFactory interfaces, collectors, units, sampling
   clocks, process/cgroup attribution, loss accounting, privilege assumptions, and teardown.
2. Define a versioned mapping from every accepted CSB value to the corresponding ASB metric,
   including source revision, scope, unit, timestamp/window, availability reason, and overhead.
3. Make monitoring ownership explicit per run: either ASB-native or CSB supplies a mapped
   signal. Reject ambiguous ownership and prove no metric, process, cgroup, or sampling cost is
   double counted.
4. Exercise controlled CPU saturation, memory pressure, block I/O pressure, scheduler pressure,
   and lock/futex contention workloads with independent native oracles. Record which phenomena
   CSB actually observes; do not relabel PSI, throttling, or utilization as causal contention.
5. Test missing permissions, absent PMU/BTF/cgroup features, multiplexed counters, lost samples,
   process exit, cancellation, partial output, malformed/overflowing values, clock skew, collector
   failure, and cleanup. Every uncertain result fails closed or remains explicitly unavailable.
6. Measure collector overhead and sampling perturbation at idle and load, compare direct ASB and
   CSB-backed runs on the same immutable fixture, and define evidence-backed operating limits.
7. Run focused and full quality, privacy, formal-contract, and native platform gates; publish only
   the combinations exercised on native x86_64 and aarch64 Linux, including mainstream Linux and
   openEuler where runners exist.

## Acceptance criteria

- A pinned, license-audited CSB revision and exact build inputs are recorded; no README claim is
  accepted as behavior evidence.
- The compatibility record enumerates each accepted and rejected CSB monitor output, its unit,
  scope, sampling window, provenance, unavailable semantics, and ASB mapping.
- Controlled fixtures and independent oracles distinguish resource usage and pressure from causal
  kernel contention; support is claimed only for directly observed signals.
- Exactly one collector owns each logical metric per run. Duplicate ownership, attribution
  mismatch, stale windows, lost samples, unsupported privilege/platform state, and teardown
  uncertainty are rejected or explicitly unavailable.
- Direct-ASB and CSB-backed runs preserve cancellation, artifact, timing, and workload identity;
  bounded overhead/loss results are published for each supported native architecture/platform.
- Meaningful negative, fault, concurrency, and cleanup tests pass, and no syzkaller/generator or
  CSB installation becomes mandatory for normal ASB builds and runs.

## Evidence and completion

Record immutable ASB and CSB commits, artifact digests, licenses, exact native hosts/runners,
commands by digest, fixture/oracle definitions, raw-to-normalized mapping checks, overhead and loss
bounds, review, exact-head CI, and post-merge outcomes. Retain only redacted bounded public
fixtures; exclude credentials, prompts/responses, private paths/logs, and unrelated CSB history.
Finish only after all criteria pass and the documentation clearly separates supported monitoring,
unsupported combinations, and the independent ASB-native baseline.
