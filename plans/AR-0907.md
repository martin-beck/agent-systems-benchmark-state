# AR-0907: Classify hosted runner evidence without weakening native qualification

## Outcome

Distinguish functional portability exercised on a rolling hosted x86_64 runner from immutable
native qualification evidence. A hosted patch-release change must never be accepted as the
reviewed Ubuntu 24.04.4 release, must never produce or overwrite a native qualification artifact,
and must not erase the historical AR-0848 evidence.

## Evidence contract

1. Retain the exact AR-0848 validator and its Ubuntu 24.04.4 evidence unchanged. Ubuntu 24.04.5,
   any other patch, malformed release data and ambiguous release identity remain rejected by the
   native qualification validator.
2. Add a closed, bounded hosted-portability projection with an explicit non-qualification kind,
   runner label, architecture, observed public distribution identity, immutable source commit and
   tree, executed check digests/statuses, and fixed limitation tokens. Exclude hostnames, private
   paths, environment values, credentials and raw command diagnostics.
3. On a rolling hosted runner, execute the reviewed functional checks and emit only the hosted
   portability projection unless the observed release independently satisfies the unchanged exact
   native validator. Never fabricate, rename or upload hosted output as native evidence.
4. Upload artifacts conditionally by evidence kind: exact native evidence only after successful
   immutable qualification; hosted portability evidence under a distinct name and schema. Missing,
   malformed or partial output fails the producing step rather than being silently skipped.
5. Preserve x86_64 hosted portability and pinned QEMU AArch64 as CI capacity. Native AArch64 remains
   optional and non-blocking. Public evidence must refer only to an authorized x86_64 development
   host and never include private infrastructure names.

## Negative and positive tests

- Prove the unchanged native validator accepts the exact reviewed 24.04.4 identity and rejects
  24.04.5 rather than treating patch releases as equivalent.
- Validate one canonical hosted-portability fixture and close the mutation partition for unknown or
  missing fields, extra identities, wrong kind/schema, wrong architecture, unpinned source identity,
  unsafe text, oversized input, duplicate checks, failed or omitted checks and forbidden private
  material.
- Exercise workflow artifact selection: a rolling 24.04.5 runner emits and uploads only distinct
  hosted-portability evidence; exact 24.04.4 may follow the native qualification path; validator or
  check failures create neither successful artifact nor qualification claim.
- Add adversarial tests for symlinked/non-regular outputs, stale pre-existing output, truncated JSON,
  raw stderr/private sentinel suppression and failure before upload classification.

## Approved partial-evidence amendment

The rolling hosted service does not guarantee the exact native sandbox prerequisites used by the
immutable Ubuntu 24.04.4 qualification cell. Independent review and coordinator approval activated
signed amendment `f6472dc2b440cbfa20a78781815792ea22d75cb4`. The following rules replace the
requirement that unavailable native sandbox capability must make the hosted classification itself
fail:

1. Process and metrics checks remain mandatory and must pass. Any nonzero exit, timeout, oversized
   output, malformed result, or source-identity drift remains a hard failure and produces no
   artifact.
2. The reviewed sandbox suite must still execute. Only its bounded, fixed
   `native sandbox capability unavailable` result at exit zero may produce an unavailable
   classification. A failing sandbox test is never converted to unavailability.
3. An unavailable sandbox result is represented only as
   `qualification=functional-portability-partial`, a closed `sandbox.status=unavailable` object
   containing command/output digests and byte count, and the fixed
   `native-sandbox-unavailable` limitation. These fields are semantically bound; a missing,
   contradictory, or forged combination fails validation and is deleted before upload.
4. Partial hosted evidence is diagnostic evidence that process and metrics portability passed. It
   does not establish full hosted functional portability, native qualification, sandbox support,
   performance comparability, release qualification, or native AArch64 capacity. Every downstream
   consumer requiring any of those properties must reject the partial qualification token.
5. A successful workflow conclusion for a partial projection means only that evidence
   classification and retention completed as specified. It must not be interpreted as proof that
   all three capabilities passed. Full hosted portability continues to require
   `qualification=functional-portability-only` with all three checks marked `passed`.
6. The unchanged exact Ubuntu 24.04.4 native validator and historical evidence remain authoritative.
   Hosted partial evidence can never be renamed, promoted, or substituted for native evidence.

AR acceptance is therefore “the rolling image produced an honest full-or-partial closed projection,
and every downstream claim is gated by the exact qualification token,” rather than “the rolling
image passed all three functional capabilities.”
