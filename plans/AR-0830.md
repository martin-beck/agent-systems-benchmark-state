# AR-0830: Provision hardened development host ASB runner capacity

## Outcome

Create one or more explicitly labeled ASB GitHub Actions runners on the development host, next to
existing runners but with separate directories, service identities, leases, caches, logs, and reset
policy. This task provisions and canary-tests capacity only; general workflow routing remains disabled
until independent qualification and a separately reviewed activation transition.

## Dependencies and ownership

Dependencies: AR-0002, AR-0003, AR-0103.
Owned paths: development host ASB runner installation/service configuration, runner labels and leases,
reset/cleanup scripts, sanitized inventory and operational documentation. Existing Relay runner
paths and services are read-only dependencies.
Branch: feature/development-host-runner-capacity. Worktree: agent-systems-benchmark-development-host-runner-capacity.

## Work sequence

1. Inventory architecture, distribution, kernel, CPU/memory/storage/network ceilings, existing
   runner services, ownership, and reachability without exposing hostnames, addresses, credentials,
   tokens, or private logs.
2. Resolve a dedicated runner root beneath the configured ASB storage root, which must itself resolve
   beneath `/srv/data/projects`; reject symlinks, traversal, other filesystems, and any root shared with
   another project. Keep installation, workspaces, caches, logs, leases, artifacts, and temporary data
   beneath that root and use a dedicated least-privilege service identity.
3. Configure the runner with no default labels. Assign only an exact, versioned ASB capability label
   set and a pseudonymous runner name; fail closed if GitHub reports any default, missing, unexpected,
   stale, architecture-mismatched, or Relay label.
4. Fence workspaces, caches, artifacts, processes, cgroups, containers, and network policy from
   existing Relay runners. Persist expiring leases and refuse concurrent or stale ownership.
5. Add idempotent setup, health, reset, orphan cleanup, and uninstall paths. Reset must remove
   untrusted checkout/build state while preserving only bounded operator diagnostics.
6. Keep registration tokens, SSH material, package credentials, and private infrastructure
   identity outside both repositories and all public artifacts.
7. Expose only a protected, manually dispatched qualification canary. Do not route ordinary trusted
   jobs or public pull requests to this capacity in AR-0830; activation follows successful AR-0832
   qualification and independent review.

## Acceptance criteria

- A clean development-host ASB runner is independently addressable only by its complete exact label
  set, has default labels disabled, and cannot consume a Relay, partial-label, or generic self-hosted
  job.
- The service starts after reboot, runs least-privileged, uses isolated roots and caches, and
  fails closed when its lease, label, architecture, disk, or health contract is invalid.
- Setup and reset are idempotent. Faults are injected only inside the dedicated runner boundary:
  project-local quota or disposable filesystem exhaustion, runner-namespace network loss, service
  restart rather than host reboot unless separately authorized, expired lease, process escape, and
  orphaned workspace tests leave no cross-runner residue.
- Existing Relay services remain unchanged and healthy before and after every ASB operation.
- Runner names are pseudonymous and diagnostics redact hostnames, addresses, usernames, absolute
  runtime paths, GitHub registration material, and runner contexts. No secret, credential, private
  path, prompt, response, or raw log enters source, public state, job output, or release artifacts.
- Public-PR caches and artifacts cannot seed this runner's trusted cache namespace; all retained
  inputs are trust-separated and content-verified before use.

## Evidence and completion

Record exact runner/tool hashes, service identity and permissions, sanitized platform inventory,
lease transitions, service restart/reconnect, reset/uninstall, isolation negatives, no-default-label
evidence, canary routing, and independent review. Do not publish a host reboot claim unless a separate
authorization and bounded test exists.
Completion requires exact-tree CI and post-install/post-reset verification.
