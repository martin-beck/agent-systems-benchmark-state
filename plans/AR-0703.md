# AR-0703: Provision native platform qualification capacity

## Outcome

Provide maintained disposable booted Debian stable and openEuler LTS qualification capacity on
genuine x86_64 and aarch64 processors so AR-0702 can execute its native kernel matrix without
substituting containers, cross-builds or emulation.

## Dependencies and ownership

Dependencies: AR-0701, AR-0103, AR-0201, AR-0401.
Owned paths: native-lab provisioning, reservation, teardown and sanitized evidence tooling.
Branch: feature/native-platform-lab. Worktree: agent-systems-benchmark-native-platform-lab.
One worker owns this task. Credentials, provider configuration and private infrastructure identity
remain outside both public repositories.

## Work sequence

1. Select disposable or reprovisioned genuine x86_64 and aarch64 capacity with explicit cost and
   availability ceilings; never incur spend without coordinator authorization.
2. Boot the exact pinned Debian stable and openEuler LTS releases and record kernel, architecture,
   firmware or virtual-machine boundary, image provenance and tool versions without host identity.
3. Isolate trusted immutable native qualification revisions from public pull-request execution,
   allocate exclusive benchmark resources and fence concurrent reservations.
4. Exercise provisioning, health checks, credential injection, artifact retrieval, teardown,
   orphan recovery and repeated cleanup, retaining only bounded redacted evidence.
5. Hand the verified capacity contract and immutable runner evidence to AR-0702 for its cgroup,
   PSI, cancellation, cleanup, LSM and workload qualification matrix.

## Acceptance criteria

- Booted Debian stable and openEuler LTS are available on genuine x86_64 and aarch64 processors;
  the guest or host kernel matches the recorded distribution cell and no QEMU/TCG or architecture
  emulation is accepted as native evidence.
- Every host is disposable or reset to a reviewed image, has an exclusive expiring reservation,
  bounded CPU/memory/storage/network resources, and a tested teardown plus orphan-recovery path.
- Persistent credentials are least-privilege, injected outside source, redacted from outputs and
  revoked or rotated after use. Untrusted public pull-request code never executes on a persistent
  credential-bearing runner.
- Cost authorization, per-run and aggregate ceilings, automatic stop conditions, capacity health,
  retry limits and unavailable-provider behavior fail closed before provisioning side effects.
- Evidence binds platform ID, exact release, native architecture, kernel release, immutable source
  revision, run ID and artifact digest, while excluding hostnames, addresses, account identifiers,
  credentials, prompts and raw private logs.

## Tests and negative evidence

Test wrong architecture, wrong distro or kernel, QEMU/TCG/emulation detection, stale and concurrent
leases, unavailable capacity, missing or excessive cost authorization, partial provisioning,
credential lookup and redaction failures, interrupted teardown, leaked process/cgroup/storage/network
resources, artifact corruption and replayed run IDs. Prove a complete provision-run-collect-destroy
cycle for all four required cells and independently audit residual resources and billing state.

## Evidence and completion

Record provider/tool/image versions and immutable digests, commands by digest, bounded costs,
availability observations, four native run artifacts and cleanup audits. Completion requires
independent immutable-head review, exact-head CI, integration and a post-merge reprovisioning check.
Unsupported or temporarily unavailable capacity remains explicit and blocks dependent native claims.
