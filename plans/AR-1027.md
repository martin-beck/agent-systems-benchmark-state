# AR-1027: Publish the verified asb-tui release

## Outcome

Publish the first release that a supported ASB installation may obtain with `asb tui install` and
promote the stable channel only after the public artifacts themselves pass independent verification.

## Dependencies and ownership

Dependencies: AR-0823, AR-0903, AR-1012 and AR-1026.
Repository: `martin-beck/asb-tui`, coordinated with the exact released ASB version.
Owned paths: release workflow/configuration, release status/channel index, signed manifest and
public release documentation/evidence. Branch: `release/asb-tui-verified-channel`.
Worktree: `agent-systems-benchmark-asb-tui-verified-release`.

## Work sequence

1. Select the exact qualified asb-tui commit/tree and exact released ASB/protocol compatibility.
2. Build Linux x86_64 and required pinned-QEMU AArch64 release candidates from clean pinned inputs.
3. Produce executable, source archive, license report, SPDX SBOM and provenance statement; bind all
   sizes/digests plus source, toolchain, workflow, coordinator and quality identities.
4. Create and sign the closed release manifest under the dedicated namespace and create a signed
   annotated immutable version tag without moving or replacing any prior tag.
5. Run hosted and trusted exact-tag builds, compare reproducible outputs and independently verify a
   draft release download before publication.
6. Publish the GitHub release, then execute public online and offline `asb tui install` from clean
   supported systems and prove launch, run/reconnect, upgrade/rollback and remove.
7. Sign and publish the stable-channel index only after those checks pass. Change channel status to
   verified/installable only when every machine-readable promotion condition is true.
8. Re-run public install and rollback after promotion, restore permanent branch protections and
   record exact final evidence.

## Acceptance criteria

Every published asset is immutable, authenticated, complete and reproducibly attributable; ASB
selects only the compatible release; public installation works without caller trust material;
rollback preserves the last verified version; no critical/high audit finding remains; and channel
metadata never claims more than exact platform and workflow evidence proves.

## Evidence

Record tag object, commits/trees, artifact sizes/digests, signatures, SBOM/license/provenance checks,
hosted/trusted run IDs, independent verifier output, clean-install matrices, rollback results,
protection settings and post-release public command output. CI artifacts alone are not releases.
